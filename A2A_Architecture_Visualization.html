Why A2A? The Missing Link in Multi-Agent Systems

Why you understand the individual agents, but connecting them felt confusing.

The Fundamental Realization:
In a single Python script or LangGraph notebook, agents talk by calling Python functions directly or passing Python dictionaries in memory.

But in real production:
  • Your SQL Agent is built on LangChain with database credentials inside a private enterprise VPC.
  • Your Podcast Agent is built on Google ADK with specialized neural voice models.
  • Your RAG Agent is hosted as an independent microservice with its own vector index.
You cannot import sql_agent from another cloud or another server!

A2A is the universal bridge. It turns every agent into an independent web service speaking standard JSON-RPC 2.0 over HTTP. It doesn't matter what language or framework they are built in!

1. Agent Cards (.well-known)

Every agent serves its own "resume" at /.well-known/agent-card.json. The orchestrator doesn't need to guess what an agent can do; it reads the card's advertised skills and endpoints.

2. Boundary Opacity

Agent A never sees Agent B's system prompts, memory heap, or database passwords. Agent B is a secure black box that accepts a task and returns an Artifact.

3. Stateful Task Lifecycles

Instead of quick stateless API calls, A2A assigns a Task ID that transitions from submitted → working → completed.

A2A vs. MCP: Why Both Use JSON-RPC 2.0 and How They Differ

A common question is: "Does A2A use JSON-RPC 2.0 because MCP uses the same protocol?"
Yes, both use JSON-RPC 2.0 as their wire format, but they solve entirely different problems in the AI stack: JSON-RPC 2.0 is an open, lightweight, transport-agnostic standard that gives both protocols request/response tracking (id), structured error handling (code, message), and streaming notifications. However, their architectural responsibilities are completely separate:

Dimension Anthropic MCP (Model Context Protocol) Google A2A (Agent2Agent Protocol)
Primary Relationship Host-to-Tool / Client-to-Resource (1:N tools) Agent-to-Agent / Peer-to-Peer (Collaborative federation)
Who Reasons? ❌ No reasoning on server. Tool servers are passive functions returning raw text/data. ✅ Both sides have cognitive loops. Recipient agent runs its own LLM, prompts, and planners.
Operation Granularity Micro-operations: tools/call, resources/read, prompts/get Macro-missions: message/send, tasks/create, tasks/get
Boundary Opacity Transparent: Host sees function signatures, arguments, and handles tool errors. Opaque: Caller delegates a goal; callee's internal prompts, model weights, and tools are hidden.
Deliverables Raw string / JSON returned into the LLM prompt Structured Artifacts (scripts, audio, databases) attached to a stateful Task
Discovery Tool schemas via tools/list Agent Card at /.well-known/agent-card.json declaring skills and input modes

🎯 How A2A Understands User Queries & Routes to the Right Agent

In A2A, routing is never hardcoded. The Gateway or Orchestrator uses a 3-step Capability Matching Engine:

1. Agent Card Inspection

The Gateway reads the published Agent Cards at /.well-known/agent-card.json. Each card advertises specific skills (e.g. Secure Read-Only SQL Querying, FAISS Knowledge Retrieval, Podcast Dialogue Synthesis).

2. Semantic Intent Matching

The incoming query is evaluated against all advertised skills. Match scores (0–100%) and confidence ratings are calculated for every candidate agent.

3. JSON-RPC Dispatch / Composite Orchestration

If a single agent dominates, a direct message/send payload is dispatched. If the query spans multiple domains (e.g. database + podcast), the Multi-Agent Orchestrator executes a sequential pipeline.

⚡ Real Agent Invocation vs. Deterministic Fallbacks:
When an agent is invoked, it runs its real internal framework: Google ADK (Agent Development Kit) for the Podcast Agent and LangChain + LangGraph for the SQL and RAG agents. If your Google Gemini API key has an active billing account, a live LLM call is made to Gemini. If the API returns HTTP 403 (due to an outstanding balance on Google AI Studio), the agents safely capture the live API error and execute deterministic SQLite tools, PII masking, and FAISS vector retrieval so your system never crashes!

Step 1: Dynamic Discovery via Agent Cards

The Orchestrator client sends an HTTP GET to /.well-known/agent-card.json for each agent. It discovers:
• SQL Agent advertises: query_user_accounts and hitl_pii_governance
• RAG Agent advertises: semantic_knowledge_retrieval and grounded_qa_with_citations
• Podcast Agent advertises: generate_podcast_script and synthesize_podcast_audio

How to Start the Servers: Gateway vs. Individual

Understand how to run all three agents together or as isolated microservices.

Mode 1: Unified Gateway (All in 1)

Port 8000

Starts a single FastAPI web application that mounts all three agents under separate path namespaces. Ideal for local testing and quick development.

Terminal 
uv run python a2a/main.py --server --port 8000

Live Endpoints:

  • http://127.0.0.1:8000/.well-known/agent-card.json (Federated Root)
  • http://127.0.0.1:8000/podcast/a2a (Podcast ADK RPC)
  • http://127.0.0.1:8000/sql/a2a (SQL LangChain RPC)
  • http://127.0.0.1:8000/rag/a2a (RAG LangChain RPC)

Mode 2: Individual Microservices

Ports 8001, 8002, 8003

Runs each agent on its own dedicated port and operating system process. Simulates real enterprise cloud deployment where agents live on separate machines.

Terminal (Start All 3 at once) 
uv run python a2a/main.py --start-individual-servers

Or start individually in separate terminal windows:

Individual Commands 
# Terminal 1: Podcast Agent on Port 8001
uv run python a2a/server.py --agent podcast --port 8001

# Terminal 2: SQL Agent on Port 8002
uv run python a2a/server.py --agent sql --port 8002

# Terminal 3: RAG Agent on Port 8003
uv run python a2a/server.py --agent rag --port 8003
How the Orchestrator Connects to Individual Servers:
When running in individual mode, run the demo with the --demo-individual flag:
uv run python a2a/main.py --demo-individual

The Orchestrator automatically talks to http://127.0.0.1:8001/a2a (Podcast), http://127.0.0.1:8002/a2a (SQL), and http://127.0.0.1:8003/a2a (RAG)!

File-by-File Architecture of the A2A Package

A clear breakdown of every single file inside the a2a/ folder.

📄 a2a/models.py

Canonical Schemas

What it does: Defines the 5 core Pydantic data models required by the A2A v1.0 protocol specification.

  • Part: Atomic multimodal payload block (text, json data, media_type, url).
  • Message: One conversational turn with role ("ROLE_USER" / "ROLE_AGENT") and contextId.
  • Artifact: Formal structured deliverable (e.g. script, dataset) produced by an agent.
  • Task: Stateful unit of work tracking lifecycle states (submitted, working, completed).
  • AgentCard: Standard discovery manifest schema advertising skills and supported interfaces.
  • JsonRpcRequest / JsonRpcResponse: Transport envelopes.

📄 a2a/agent_cards.py

Agent Manifests

What it does: Declares the official Agent Card for each of our three agents.

  • get_podcast_agent_card(): Advertises generate_podcast_script and synthesize_podcast_audio skills.
  • get_sql_agent_card(): Advertises query_user_accounts and hitl_pii_governance skills.
  • get_rag_agent_card(): Advertises semantic_knowledge_retrieval and grounded_qa_with_citations skills.
  • export_all_cards(): Utility to dump cards to static JSON files in a2a/cards/.

📄 a2a/server.py

FastAPI Protocol Engine

What it does: The web server that bridges incoming JSON-RPC HTTP calls into the internal agent python code.

  • execute_agent_work(): Routes prompts to run_sql_agent_query(), run_rag_agent_query(), or Podcast studio.
  • handle_jsonrpc(): Parses JSON-RPC methods: message/send, tasks/get, tasks/cancel.
  • create_gateway_app(): Launches all three agents on Port 8000.
  • create_standalone_agent_app(): Launches a single agent on an independent port (8001, 8002, 8003).

📄 a2a/client.py

Reusable Consumer Client

What it does: The Python client that anyone can use to call an A2A agent over HTTP.

  • get_agent_card(): Performs HTTP GET to /.well-known/agent-card.json and parses into an AgentCard.
  • send_message(): Formulates a JSON-RPC message/send request and extracts output + artifacts.
  • get_task(): Polls task state via tasks/get.

📄 a2a/orchestrator.py

Cross-Agent Pipeline

What it does: Connects all three agents in sequence: SQL Agent → RAG Agent → Podcast Agent.

  • Discovers all 3 cards dynamically.
  • Queries SQL Agent for Alice Smith's balance (PII redacted).
  • Queries RAG Agent for Google Gemini architecture facts.
  • Pipes both outputs into Podcast Agent to generate a 2-speaker audio/script episode!

📄 a2a/main.py

CLI Entry Point

What it does: Command-line interface to start servers, run demos, query agents, and inspect cards.
